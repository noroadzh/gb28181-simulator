# Design

## Context

当前 `internal/interface/http/channels.go` 中的 `generateChannelID` 函数实现生成了 `${nodeID}_${seq}` 格式的伪 ID（如 `34020000002000000001_1`），与已 spec'd 的 `channel-id-auto-gen` 规范不符（规范要求 20 位纯数字 GB/T 28181 编码）。同时 `channelResponse` 结构体未包含规范要求的 `auto_generated` 字段。前端 `ChannelListView.vue` 复制了同样的错误预填逻辑。账号管理页 `AccountsView.vue` 错误地将 `api.listNodes()` 返回的数组当作 `{nodes: [...]}` 包装对象处理。

## Goals / Non-Goals

**Goals:**

- 后端 `generateChannelID` 严格按 GB/T 28181 20 位规范生成纯数字 ID
- 后端 `channelResponse` 返回 `auto_generated` 布尔字段
- 前端不预填通道 ID，留空由后端生成
- 前端校验规则与后端 `isValidChannelID` 完全对齐（20 位纯数字）
- 前端账号管理页正确解析节点列表 API 响应

**Non-goals:**

- 不修改 GB/T 28181 SIP 信令层的任何行为
- 不修改媒体源类型或配置逻辑
- 不新增通道级 API 端点
- 不重构已有的通道媒体源编辑 UI

## Decisions

### 决策 1：`generateChannelID` 重写为生成 20 位纯数字

**方案**：将 `generateChannelID` 改为按 `前6位行政码 + 00 + 13 + 10位补零序号` 拼接：

- 节点 ID 已通过 `model.ParseNodeID` 校验，必然是 20 位纯数字，取其前 6 位作为行政码
- 行业码 `00` 与类型码 `13` 在 GB/T 28181 规范中分别表示"非行业专用"与"通道"
- 序号部分用 `%010d` 格式化（10 位左补零），从 `maxSeq+1` 开始
- mutex（`autoIDMu`）保护范围不变：仅对自动生成路径加锁

**备选方案 A**：保持 `${nodeID}_${seq}` 格式，仅在 spec 中放宽为"非 20 位纯数字也可"。

- 拒绝：GB/T 28181 规范明确通道 ID 必须为 20 位数字编码；放宽后与下游 GB 平台/设备互操作时会失败

**备选方案 B**：使用 UUID 替代国标编码。

- 拒绝：GB/T 28181 协议层面要求通道 ID 必须是 20 位国标编码，UUID 会被下游平台拒绝

### 决策 2：响应字段从内部传递"是否自动生成"标志

**方案**：在 `handleChannelAdd` 中通过局部变量 `autoGenerated` 记录 ID 是否来自自动生成路径，然后传递给 `newChannelResponse`。

- 显式 ID 路径：`autoGenerated = false`
- 空 ID 路径（自动生成）：`autoGenerated = true`
- `newChannelResponse` 新增 `AutoGenerated bool` 字段，JSON tag 为 `auto_generated`

**备选方案 A**：在 `model.Channel` 上加 `AutoGenerated` 字段。

- 拒绝：模型层与 HTTP 表现层职责混叠；AutoGenerated 只是 HTTP 响应的元数据，不属于领域模型

### 决策 3：前端移除预填，由后端自动生成

**方案**：`openAddChannel()` 不再调用 `suggestChannelID()`，将 `addChForm.id` 初始值设为 `''`。`chIdRule` 校验规则改为"非空时必须是 20 位纯数字"（空值合法）。

- 用户体验：用户保留为空提交时，通道创建成功并展示实际生成的 20 位 ID
- 错误处理：若后端返回的 ID 与用户输入不一致（理论上不应发生），前端以响应中的 `id` 字段为准

**备选方案 A**：保留前端预填，但修正预填格式为正确的 20 位数字。

- 拒绝：预填是脆弱的，下游平台/设备的国标编号规则可能有差异；让后端统一生成更稳健

### 决策 4：`AccountsView` 改为直接使用数组

**方案**：`loadNodes()` 中：

```js
async function loadNodes () {
  try {
    nodes.value = await api.listNodes()  // 直接赋值数组
    ...
  }
}
```

移除 `j.nodes || []` 包装。

## Risks / Trade-offs

[风险 1] 自动生成的通道 ID 与用户期望的国标编号规则可能不匹配（例如某些下游平台要求第 7-8 位必须是特定行业码如 `13` 而非 `00`）
→ 缓解：spec 中明确写明 `00` 是 GB/T 28181 规范中"非行业专用"的合法取值；如需扩展行业码范围，后续可加配置项

[风险 2] 后端 `generateChannelID` 修改后，存量使用 `${nodeID}_${seq}` 格式的通道（如果有）会变成"非法 20 位"格式，导致 `isValidChannelID` 校验失败
→ 缓解：本次 fix 当前后端实现从未按 spec 正确实现，因此存量数据中**不应该存在**已通过 spec 验证的自动生成通道；若有用户反馈保留旧格式通道为已知问题，本次只改新生成路径，不改历史数据

[风险 3] 前端 `channel-web-ui` 当前 spec 规定"channel_id 输入框 20 位国标编码校验"，新 delta spec 改为"非空时 20 位纯数字"——可能与 spec 已有 requirement 产生冲突
→ 缓解：delta spec 作为"修正原有 spec"使用 ADDED Requirements；apply 阶段同时更新主 spec 移除冲突 requirement

[风险 4] `AccountsView` 改回直接用数组后，若后端某天引入 `{nodes: [...]}` 包装，前端会再次失效
→ 缓解：delta spec 明确写出"GET /v1/nodes 返回 JSON 数组"作为契约；后续后端若要改包装形式需先更新 spec
